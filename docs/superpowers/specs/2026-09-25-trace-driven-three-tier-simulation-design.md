# Trace-Driven Three-Tier Simulation Design

**Date:** 2026-09-25  
**Status:** Approved for implementation planning

## 1. Purpose

This increment turns Aether from a live mobility visualization into a
reproducible experimental platform for mobility-aware workload placement. It
combines real OpenSky mobility observations with real production workload
traces while preserving the provenance boundary between observed,
trace-derived, modelled, and simulated data.

The system will run Microsoft Azure Functions and Google Borg as separate
scenarios over the same fixed European far-edge, edge, and cloud topology. It
will compare deterministic scheduling policies using a flow-level network
model and a combined objective without hiding the individual latency,
reliability, utilization, transfer, and energy metrics.

This increment establishes deterministic baselines. Prediction,
reinforcement learning, Kubernetes execution, packet-level networking, and
mobile compute nodes remain outside its scope.

## 2. Success Criteria

The increment is complete when:

- official-schema Azure Functions and Google Borg inputs can be normalized
  into the same versioned workload contract;
- each trace runs as a separate reproducible scenario with the same topology,
  mobility timeline, capacity profile, seed, and scheduler policies;
- a full directed graph represents fixed far-edge, edge, and cloud sites and
  flow-level network behavior;
- four deterministic baseline schedulers can be compared on identical inputs;
- node capacity, link bandwidth, queueing, transfer, execution, migration,
  rejection, and deadline behavior are simulated without over-allocation;
- every result records field-level provenance and the complete experiment
  configuration;
- live and completed runs are observable through the API and a read-only
  control-room experiment view;
- the same inputs and seed produce byte-identical normalized workload
  artifacts and equivalent result summaries; and
- one hour from each trace can be replayed against every baseline policy on
  the starter European topology to produce a comparison report.

## 3. Scientific Boundaries and Provenance

OpenSky aircraft density is not treated as measured compute demand. The two
real inputs are independent:

- OpenSky supplies observed position and time for geographic mobility.
- Azure Functions or Google Borg supplies trace-derived workload behavior.

The scenario model assigns trace workloads to geographic origins using the
current OpenSky density distribution. That assignment is modelled, not
observed. Infrastructure topology, capacity, network behavior, energy, and
cost are simulated.

Every canonical workload records provenance for each field using these
categories:

- `observed`: directly obtained from a live external observation;
- `trace_derived`: directly obtained or deterministically transformed from a
  public production trace;
- `modelled`: generated by a named, versioned scenario model; and
- `simulated`: produced by the discrete-event simulator.

Run artifacts include the source trace, source version, source and normalized
checksums, adapter version, topology version and checksum, capacity profile,
mobility assignment model, scale factor, time acceleration, random seed,
scheduler policy, objective weights, and simulator version.

Trace preparation and simulation are independent of the live ingestor. Raw

## 5. Canonical Workload Contract

Each normalized workload contains:

```text
identity
  workload_id
  scenario_id
  source_trace
  source_record_id

timing
  arrival_time
  expected_duration
  deadline
  priority

resources
  requested_cpu_millicores
  requested_memory_mb
  requested_gpu_units
  input_data_bytes
  output_data_bytes
  movable_state_bytes

behavior
  preemptible
  restartable
  migration_allowed

geography
  origin_h3_cell
  origin_latitude
  origin_longitude

provenance
  field_provenance
  source_trace_version
  adapter_version
```

Resource values are non-negative. Arrival, duration, and deadline use the
simulation clock. Stable identifiers are deterministic over scenario,
source-record identity, adapter version, and seed.

### 5.1 Azure Functions Adapter

The Azure scenario represents short-lived, bursty, latency-sensitive
serverless work.

- Invocation arrival and duration come from the selected Azure trace.
- Available application memory characteristics come from the trace.
- Missing CPU, deadline, input, output, and movable-state values come from a
  named adapter model and are marked `modelled`.
- Functions are restartable by default. Preemption and migration eligibility
  are explicit adapter outputs rather than simulator assumptions.

### 5.2 Google Borg Adapter

The Borg scenario represents longer-running cluster tasks.

- Submission time, duration, requested CPU, requested memory, priority, and
  available scheduling attributes come from the selected Borg trace.
- Missing deadline, transfer-size, and movable-state values come from a named
  adapter model and are marked `modelled`.
- Preemption, restart, and migration eligibility follow trace attributes when
  available and versioned adapter rules otherwise.

### 5.3 Geographic Origin Assignment

Both scenarios use the same deterministic origin-assignment algorithm. For
each replay window, valid OpenSky-derived H3 density cells form a weighted
distribution. Workload origins are sampled from that distribution using the
run seed and stable workload identity.

The assignment is always marked `modelled`. A bounded last-valid snapshot may
be used when the live source becomes stale. Once that bound expires, the run
pauses rather than generating new mobility.

## 6. Trace Preparation

A trace-preparation CLI accepts an official trace download or a local copy. It
will:

1. verify the expected checksum and input schema;
2. select a documented time range and source-specific partition;
3. apply deterministic sampling with an explicit scale factor;
4. normalize source records into canonical workloads;
5. write a compact Parquet replay artifact; and
6. write a manifest with all source, transformation, model, and checksum
   metadata.

The repository contains small official-schema fixtures but not the raw public
datasets. Full datasets remain external research inputs.

Scaling preserves temporal shape. Sampling changes the number of workloads,
not individual resource requests. Optional time acceleration changes replay
speed and is recorded independently from sampling. Identical inputs,
configuration, and seed produce identical normalized output.

Malformed rows are counted with reason codes. They are never silently repaired
or omitted from the preparation report.

## 7. Three-Tier European Topology

The topology is a versioned external document containing arbitrary nodes and
directed links. No site or tier count is hard-coded.

### 7.1 Node Model

Each fixed node has:

- stable identifier and display name;
- tier: `far_edge`, `edge`, or `cloud`;
- latitude and longitude;
- CPU, memory, and optional GPU capacity;
- queue capacity and execution concurrency limits;
- energy and operating-cost profile; and
- one or more failure domains.

Far-edge sites use real major European airport coordinates, edge sites use
real metro locations, and cloud nodes use real European cloud-region
geography. All capacity, energy, and cost values are explicitly simulated.

### 7.2 Link Model

Each directed link has:

- source and destination node;
- propagation latency;
- total bandwidth;
- transfer cost and energy coefficients;
- availability state; and
- failure domains.

Links may be asymmetric. The graph permits redundant and lateral paths; it is
not restricted to a hierarchy.

### 7.3 Expansion Profiles

The initial topology profiles are:

- `eu-small-v1`: 20 far-edge sites, 8 edge sites, and 4 cloud regions;
- `eu-medium-v1`: approximately 100 far-edge sites, 25 edge sites, and 8
  cloud regions; and
- future research profiles containing thousands of nodes and links through
  the same schema.

The engine uses adjacency lists and cached path calculations. Larger runs may
execute headlessly and may partition visualization data without changing
simulation semantics or contracts.

## 8. Flow-Level Network Simulation

The simulator is discrete-event and flow-level. A transfer is represented by
its source, destination, path, byte count, start time, and remaining bytes.
It does not simulate individual packets, TCP congestion windows,
retransmissions, or protocol headers.

Propagation latency is the sum of link latencies. Concurrent flows share each
link's available bandwidth. A flow's progress is limited by the bottleneck on
its current path. Flow arrivals, completions, route changes, link failures,
and link recovery trigger deterministic bandwidth reallocation.

Network paths account for direction, availability, propagation latency,
current congestion, transfer cost, and energy. Failures invalidate affected
cached paths and trigger recalculation. A disconnected workload is queued,
recovered according to policy, or rejected at its deadline.

## 9. Compute Simulation

Workloads move through these states:

```text
arrived -> placed -> transferring -> queued -> running -> completed
                    |             |          |
                    +-------------+----------+-> rejected or failed
```

Placement reserves no compute until required input transfer completes.
Execution reserves CPU, memory, GPU, and concurrency capacity atomically.
The simulator never over-allocates a physical resource. Queue ordering and
admission behavior belong to the selected scheduling policy.

Migration transfers the workload's movable state and consumes link bandwidth,
time, energy, and cost. The destination begins execution only after migration
completes and capacity is acquired. Non-migratable workloads remain on their
assigned node or fail according to the experiment's failure policy.

Workloads whose minimum resource request exceeds every eligible node are
marked `unschedulable`; they do not wait indefinitely or disappear.

## 10. Deterministic Baseline Schedulers

Version one supplies four policies:

1. `cloud_only`: selects the nearest feasible cloud node.
2. `nearest_feasible`: selects the feasible node with the lowest estimated
   end-to-end latency.
3. `resource_first`: favors utilization balance and queue capacity while
   accepting additional network latency.
4. `balanced`: combines compute availability, path latency, transfer time,
   queue delay, deadline risk, migration cost, transfer cost, and energy using
   explicit recorded weights.

Each policy consumes the same immutable simulation view and produces a
placement or queue decision with an explanation. Policies cannot mutate
simulator state directly.

Azure and Borg run separately. Within a trace scenario, every policy receives
the same normalized workloads, origins, topology, capacities, mobility
timeline, failure schedule, and seed.

## 11. Metrics and Combined Objective

The combined objective is recorded as a weighted score, but every component
is reported independently:

- completion, rejection, failure, and unschedulable rates;
- deadline misses;
- queue, network, execution, and end-to-end latency;
- p50, p95, and p99 latency;
- CPU, memory, and GPU utilization by site and tier;
- link utilization, transferred bytes, and congestion duration;
- migrations, migration time, and migration bytes;
- estimated transfer and operating cost;
- estimated compute and network energy; and
- the combined score with its exact weights.

No report may present the combined score without its component metrics.

## 12. Runtime Integration

A new simulation service consumes prepared workload artifacts, topology,
mobility snapshots, and run configuration. It publishes versioned experiment
events to Redpanda. The state builder maintains a rebuildable Redis projection
for active runs. FastAPI exposes snapshots, run metadata, completed results,
and a dedicated WebSocket stream.

Completed runs are immutable artifact directories containing:

- run configuration;
- trace and topology manifests;
- workload and result checksums;
- time-series metrics;
- summary metrics;
- provenance summary; and
- completion or stopping reason.

Version one starts, pauses, resumes, and cancels experiments through a local
CLI. The public web application is read-only so unauthenticated visitors cannot
start expensive simulations. Authentication and a mutating control API are a
later increment.

## 13. Control-Room Experience

The existing aircraft, density, and demand map remains available. A separate
experiment workspace displays:

- trace scenario, topology, scheduler, seed, and simulated clock;
- far-edge, edge, and cloud nodes with tier-specific rendering;
- active workloads, transfers, paths, and queues;
- node and link utilization;
- deadline misses, rejected work, and failures;
- latency and utilization grouped by tier;
- provenance and run configuration; and
- completed side-by-side policy comparisons.

Live and completed experiments share one API representation. Large topology
profiles use aggregation and level-of-detail rendering rather than sending or
rendering every element at every zoom.

## 14. Failure Behavior

- Trace checksum or schema mismatch rejects preparation or run startup.
- Duplicate canonical workload identifiers reject the artifact.
- Missing nodes, dangling links, invalid coordinates, and negative resource,
  capacity, latency, bandwidth, cost, or energy values reject topology load.
- Resource and bandwidth invariants are checked during simulation.
- Node and link failures are deterministic run inputs and record their effects.
- A live mobility outage freezes the last valid distribution only for the
  configured bound, after which the experiment pauses.
- Redpanda or Redis interruption may delay observation but cannot alter the
  deterministic simulator outcome; projections rebuild from retained events
  and immutable run artifacts.
- An incomplete run records its stopping reason and last committed simulated
  timestamp.

## 15. Testing Strategy

Testing includes:

- strict contract tests for workloads, topology, run configuration, events,
  metrics, and results;
- Azure and Borg adapter tests using small official-schema fixtures;
- deterministic preparation and replay tests;
- disconnected, asymmetric, congested, failed, and recovered graph tests;
- flow bandwidth-sharing and route-invalidation tests;
- atomic CPU, memory, GPU, and execution-slot allocation invariants;
- unschedulable, queue-expiry, rejection, preemption, restart, and migration
  cases;
- identical-input comparisons across every scheduler;
- trace-to-simulator-to-Redpanda-to-Redis-to-API integration tests;
- frontend component and browser tests for topology, live metrics,
  comparisons, provenance, and large-graph level of detail; and
- bounded performance tests for `eu-small-v1` and `eu-medium-v1`.

Automated tests use fixtures and generated mobility snapshots. They never
download public traces or call OpenSky.

## 16. Acceptance Experiment

The acceptance experiment prepares one hour of Azure Functions and one hour
of Google Borg workload data with documented partitions, filters, and scale
factors. Each trace runs separately against all four baseline schedulers on
`eu-small-v1` using the same recorded OpenSky mobility timeline and failure
schedule.

The deliverable is an immutable comparison bundle containing eight completed
runs, component metrics, combined scores, provenance summaries, manifests,
checksums, and a human-readable comparison report.

## 17. Deferred Scope

The following are explicitly deferred:

- mixing Azure and Borg into one scenario;
- packet-level or protocol-level network simulation;
- mobile compute nodes;
- real provider capacity or cost claims;
- real workload geography claims;
- predictive scheduling;
- reinforcement learning;
- Kubernetes or cloud-provider execution;
- authenticated experiment control through the web application; and
- automated chaos campaigns beyond deterministic node and link failures.
